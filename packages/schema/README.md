# Maine configuration format

This package defines the saved-host document: versioned JSON holding hosts and,
from version 2, the sidebar groups they belong to. It is deliberately small, and
it is the contract between every Maine client: macOS and Android today, Linux
later.

There is no shared code, account or service of ours: a client writes this
document, reads it back, and that is the whole local storage story. On both
clients the document lives inside the encrypted vault (`passwords.maine`),
never in a plaintext file. Optional sync moves the vault as an opaque blob;
the server sees no part of this format.

The vault envelope is a second, separate contract: each client implements it
byte-for-byte so the file unlocks with the same master password everywhere.
That is why the same document can be read from either client's vault.

## Where the file lives

| Platform | Location                                                          |
| -------- | ----------------------------------------------------------------- |
| macOS    | `~/Library/Application Support/Maine/passwords.maine` (encrypted vault; the host list is inside) |
| Android  | app-private `filesDir/passwords.maine` (encrypted vault; the host list is inside) |
| Linux    | no client yet                                                     |

Each client owns its own vault. Sync, when enabled, moves the encrypted vault as
an opaque blob and never the document on its own.

Older macOS versions wrote a plaintext `hosts.json` before the unified vault
existed. It is imported once, when the first vault is created or a version-1
vault is migrated, and never written again. The old file is plaintext and stays
on disk until the user archives or removes it.

## The document

```json
{
  "schemaVersion": 2,
  "groups": [
    {
      "id": "5e1f0c2a-8b7d-4c3e-9a6f-1b2c3d4e5f60",
      "name": "Production"
    }
  ],
  "hosts": [
    {
      "id": "0f8fad5b-d9cb-469f-a165-70867728950e",
      "name": "Web server",
      "hostname": "203.0.113.10",
      "port": 22,
      "username": "",
      "group": "5e1f0c2a-8b7d-4c3e-9a6f-1b2c3d4e5f60"
    }
  ]
}
```

Version 1 is the same document without `groups` and without any host `group`.
macOS loads both versions; Android implements version 1.

The canonical definition is [`hosts.schema.json`](hosts.schema.json) (JSON Schema
2020-12).

### Top level

| Field | Type | Required | Meaning |
| ----- | ---- | -------- | ------- |
| `schemaVersion` | integer | yes | `1` or `2`. Version 2 added the optional `groups` array and each host's optional `group`. A client **must** refuse a file whose version is higher than it implements, and must not overwrite it. |
| `groups` | array of group | no | Sidebar groups, in the order the user arranged them (version 2). A group may have no hosts. Whether a group is collapsed is per-device state and is not stored here. |
| `hosts` | array of host | yes | The saved hosts, in the order the user arranged them. There is no limit on the number of entries. |

### Host

| Field | Type | Required | Meaning |
| ----- | ---- | -------- | ------- |
| `id` | string | yes | Stable identifier, generated by the client. A UUID string. A lowercase UUID is recommended, and comparisons must be case-insensitive: macOS writes uppercase `UUID().uuidString`, Android normalizes to uppercase. Clients must not derive meaning from it and must not change it when other fields are edited. |
| `name` | string | yes | The label shown in the host list. 1–128 characters. |
| `hostname` | string | yes | What is handed to the SSH client as the connection target: an IP address, a DNS name, or a `Host` alias defined in the user's own `~/.ssh/config`. No whitespace, no leading `-`. 1–253 characters. |
| `port` | integer | yes | 1–65535. `22` means "default": clients **should** omit the `ssh -p` flag so a matching `~/.ssh/config` stanza can choose the real port. |
| `username` | string | yes | 0–128 characters. The empty string means "not specified": clients **should** omit the `ssh -l` flag so the SSH stack can take the user from `~/.ssh/config`, from the key that authenticates, or from the local user name. |
| `group` | string | no | The id of the group this host belongs to (version 2). Absent means ungrouped. A value that names no group in this document **must** be treated as ungrouped. |

### Group

| Field | Type | Required | Meaning |
| ----- | ---- | -------- | ------- |
| `id` | string | yes | Stable identifier, generated by the client. A UUID string. Clients must not change it when the group is renamed. |
| `name` | string | yes | The label shown on the group header. 1–128 characters. |

### Display order

The two arrays carry the order: ungrouped hosts first, then each group in
`groups` order with its hosts in `hosts` order. Deleting a group makes its hosts
ungrouped and keeps their order; a host that points at a missing group is shown
as ungrouped.

Android currently writes version 1 and does not understand groups. It reads the
host list out of a macOS vault by ignoring the payload's `groups` array, but it
cannot read a standalone version 2 document (it refuses a `schemaVersion` above
1), and a vault it rewrites loses any groups a macOS client saved.

### What is not in the document, on purpose

* **Passwords.** They are not part of this document. A saved password lives in
  the encrypted vault payload next to the hosts, keyed by host id; the host
  list alone never contains a credential. macOS allows a host with no saved
  password and lets `ssh` prompt, or use keys and `ssh-agent`; Android requires
  a password for every host.
* **Private keys, key paths, passphrases.** None of them are stored. macOS
  leaves authentication to `~/.ssh`, `ssh-agent` and `~/.ssh/config`, so
  existing keys keep working without being copied anywhere. Android has no key
  authentication yet.
* **Known hosts, proxy commands, port forwards.** macOS leaves all of that to
  OpenSSH. Android keeps its pinned host keys in an app-private `known_hosts`
  file outside the vault. Maine only records what the user typed into its host
  list.

## Reading and writing

* **Writers must** emit every required field of every host, even when the value
  is a default (`"port": 22`, `"username": ""`). An ungrouped host omits
  `group`, so it keeps the version 1 shape.
* **Readers should** treat a missing or `null` field as its default (a fresh
  UUID for `id`, `""` for `name`, `hostname` and `username`, `22` for `port`)
  so a hand-edited file still loads. Any other type mismatch is an error the
  client must report without discarding the file.
* **Writers must** save atomically, so an interrupted write cannot leave a
  half-written document behind.
* **Writers should** keep the containing file readable only by the user
  (`0600` on POSIX systems). Both clients write inside the encrypted vault.
* Unknown properties are not allowed by the schema. A client that wants to add
  one must bump `schemaVersion` and document the migration.

## Versioning policy

`schemaVersion` is a single integer that covers the whole document.

* **Adding a required field, changing a field's meaning, or removing a field**
  requires a new version number and a documented migration path for readers.
* **Adding an optional field** still requires a new version number, because
  the schema forbids unknown properties and a reader decides what it can safely
  rewrite from the version alone.
* Clients must keep reading every version they have shipped support for, and
  must leave a file from a newer version untouched.

A version 2 example lives in
[`examples/hosts.groups.json`](examples/hosts.groups.json).
[`examples/hosts.invalid-version.json`](examples/hosts.invalid-version.json) is
a version 3 document; it exists so the validator can prove that clients reject
it. The other examples are version 1 and still validate.

## Validating a file

`tools/validate.py` checks a file, or a directory of files, against the schema.
It uses only the Python standard library.

```sh
python3 tools/validate.py                     # validates every example
python3 tools/validate.py examples/hosts.groups.json
python3 tools/validate.py --schema hosts.schema.json some-file.json
```

The vault payload is encrypted, so the script checks an extracted document or a
fixture, not a `passwords.maine` file directly.

The script supports the keywords this schema uses (`type`, `required`,
`properties`, `additionalProperties`, `items`, `$ref`, `$defs`, `const`, `enum`,
`minLength`, `maxLength`, `minimum`, `maximum`, `pattern`, plus the metadata
`default`, `title`, `description` and `format`). It refuses to run against a
schema that uses a keyword it does not implement, so it cannot silently ignore
an unknown constraint.

`format` is declared but not enforced, so `validate.py` will accept an `id` that
is not a UUID. Clients must validate identifiers themselves: macOS decodes them
as UUIDs and Android normalizes them with `UUID.fromString`.

Files whose name contains `.invalid` are expected to be rejected; everything
else must pass. The command exits non-zero if that is not the case.

## Implementing a client

A conforming client:

1. Reads the document, or starts with an empty host list when it does not exist.
2. Validates it against `hosts.schema.json` before using it.
3. Refuses (and never rewrites) a document with a higher `schemaVersion`.
4. Applies the defaults described above, and treats a `group` that names no
   group as ungrouped.
5. Uses the host only as connection parameters and leaves authentication to the
   platform: macOS runs the system OpenSSH client, so keys, agent, `ProxyJump`
   and `Match` keep working; Android uses sshj with password authentication.
6. Writes the whole document back after every change, atomically, inside the
   encrypted vault.
