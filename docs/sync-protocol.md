# Sync protocol (v1)

This is the normative wire contract between Maine clients and a Maine sync
server. It describes the HTTP surface implemented by
[`apps/sync-server`](../apps/sync-server/README.md). Client-side behavior —
when to sync, how to resolve conflicts on disk — is specified separately in
[`sync-client.md`](sync-client.md).

## The model

A **slot** is an opaque byte store. It holds one current blob plus a bounded
history of previous versions. It has no name, no owner and no metadata beyond
sizes and timestamps.

A **token** addresses exactly one slot and is the only credential to use it.
It is both the identifier and the password, like a wallet seed: whoever holds
it can read and replace the slot's contents. The server stores only
`SHA-256(token)`.

A **version** is a positive integer. Version `0` means "nothing stored yet";
the first stored blob is version `1`, and every successful write increments
it. The `ETag` of a slot is `"v<version>"`.

The **blob** is the exact `passwords.maine` file: the version-2 vault
envelope, AES-256-GCM encrypted and authenticated on the client. The server
never parses it, never transforms it and cannot decrypt it. Sync is
whole-file; there are no deltas and no per-host operations.

Design rules that follow from this:

- The server is not trusted with plaintext. Anyone who compromises it gets
  ciphertext and metadata only.
- A write is conditional on the version the client last saw. The server
  rejects stale writes; it never merges.
- The server is deliberately boring: a client that can do HTTP and file I/O
  can implement this protocol in an afternoon.

## Conventions

**Base URL.** Any HTTP(S) origin. All endpoints live under `/v1`. Requests
carry no query strings and no cookies.

**Authentication.** Every endpoint except `GET /v1/health` requires
`Authorization: Bearer <token>`.

**Token format.** 32 random bytes encoded with the alphabet
`23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (no `0`, `1`, `I`, `O`), 52 characters,
displayed as `maine-XXXX-XXXX-…` grouped in fours. Servers accept the display
form, lowercase, missing separators, and a missing `maine-` prefix; clients
should send the display form. Tokens are secrets: never log them, never send
them anywhere except the configured server, never store them in the vault.

**Request bodies.** Raw bytes, `application/octet-stream` recommended. The
server treats them as opaque.

**Timestamps.** Integer seconds since the Unix epoch, UTC.

**Errors.** JSON object `{"error": "..."}`. Responses about the state of a
slot (`409`, `412`, `428`) also carry `version`, `etag`, `size` and
`updatedAt`, and repeat the version in the `X-Maine-Version` header, so a
client can reconcile without another round trip.

**Size limit.** The server has a configurable maximum blob size (default
64 MiB, `--max-blob`). Bodies above it are rejected with `413` before they
are stored.

**Status codes.**

| Code | Meaning here |
| ---- | ------------ |
| `200` | Success with a body |
| `201` | Slot created |
| `204` | Success without a body; also "the slot is empty" on `GET` |
| `304` | `If-None-Match` matched; nothing changed |
| `400` | Malformed request (bad precondition combination, non-numeric version) |
| `401` | Missing or invalid token |
| `403` | Create secret missing or wrong |
| `404` | Unknown endpoint, or a version that is not stored |
| `409` | Write precondition failed: the slot moved on |
| `412` | `If-None-Match: *` sent, but the slot already holds a blob |
| `413` | Body exceeds the server's size limit |
| `428` | Write to a non-empty slot without any precondition |
| `500` | Server-side failure |

## Endpoints

### `GET /v1/health`

No authentication. Liveness probe.

```json
200 {"status": "ok", "name": "maine-sync-server", "version": "0.1.0"}
```

### `POST /v1/vaults` — create a slot

Creates a slot and returns its token. The token is generated by the server
and returned **exactly once**; only its hash is stored. Clients must put it
in OS secure storage before doing anything else.

- Body: optional. If non-empty, it is stored as version `1`. An empty body
  creates an empty slot (version `0`), whose first version arrives with a
  later `PUT`.
- Header `X-Maine-Create-Secret`: required only when the server was started
  with `--create-secret`.
- Precondition headers are not parsed; creation always starts fresh.

```json
201 {
  "token":   "maine-2F7K-9QX2-…",
  "version": 1,
  "etag":    "\"v1\"",
  "size":    1234,
  "sha256":  "…"
}
```

`sha256` is present when a body was stored. `403` without the right create
secret, `413` when the body is too large.

### `GET /v1/vault` — read the current blob

| Request header | Effect |
| -------------- | ------ |
| `If-None-Match` | `"v<N>"` (weak form and lists accepted), or `*`. On a match: `304`. |

Responses:

- `200` — body is the current blob. Headers: `ETag: "vN"`,
  `X-Maine-Version: N`, `X-Maine-Size`, `X-Maine-SHA256` (hex of the body),
  `X-Maine-Updated-At` (unix seconds), `Cache-Control: no-store`.
- `304` — the client is up to date. Same validators, no body.
- `204` — the slot is empty (`X-Maine-Version: 0`). This happens for a slot
  created without a body, before its first `PUT`.

Clients must verify `X-Maine-SHA256` against the received bytes before
adopting them.

### `HEAD /v1/vault`

Identical to `GET` without a body. Useful for cheap polling when the client
already has the bytes.

### `PUT /v1/vault` — store a new version

Writes are conditional by design; a client can never silently overwrite an
edit made elsewhere.

| Request header | Meaning |
| -------------- | ------- |
| `If-Match: "vN"` | Succeed only if the current version is `N`. The quotes are optional, as is the `W/` prefix. |
| `If-None-Match: *` | Succeed only if the slot is empty. `If-Match: "v0"` is equivalent. |

Rules:

- The body must be non-empty; to remove a slot, use `DELETE`.
- Send at most one precondition header; both at once is `400`.
- `If-Match: *` is not supported (`400`): it would allow a blind overwrite.
- A write with no precondition at all is allowed **only** for the first
  version of an empty slot. On a non-empty slot it is `428`.

Responses:

- `200` — stored:

  ```json
  {"version": 2, "etag": "\"v2\"", "size": 1234, "sha256": "…"}
  ```

- `409` — the slot is not at the version the client expected. The response
  body carries the current `version`, `etag`, `size`, `updatedAt`. The client
  pulls, keeps a conflict copy, and adopts the server's blob
  (see [`sync-client.md`](sync-client.md)).
- `412` — `If-None-Match: *` but the slot already holds a blob.
- `428` — precondition missing on a non-empty slot.
- `413`, `401` as usual.

### `GET /v1/vault/versions` — history metadata

Newest first. No blobs.

```json
200 {
  "versions": [
    {"version": 4, "size": 1234, "sha256": "…", "createdAt": 1730000000},
    {"version": 3, "size": 1234, "sha256": "…", "createdAt": 1729990000}
  ]
}
```

The server keeps the last `--keep-versions` (default 32) versions per slot and
prunes older ones on every write. Pruning is by count, not by age.

### `GET /v1/vault/versions/{n}` — read one old version

`200` with the same headers as `GET /v1/vault`, minus `X-Maine-Updated-At`.
`404` when the version has been pruned or never existed. Intended for
recovery, not for normal syncing.

### `POST /v1/vault/rotate` — replace the token

```json
200 {"token": "maine-7HG4-…"}
```

The new token works immediately; the old one stops working immediately. There
is no grace period and no second chance: if the response is lost in transit,
the slot becomes unreachable. Clients must treat this response like the
password it is and persist it before acknowledging the rotation in the UI.

### `DELETE /v1/vault` — wipe the slot

`204`. Deletes the slot and every stored version. Irreversible; there is no
tombstone and no recovery.

## Conflict handling in one paragraph

A `409` (or `412`) means another writer stored a version after the client
last pulled. The client resolves it locally: pull the current blob, save the
local file aside as a conflict copy, adopt the server's blob as the live
vault, update its stored version, and stop pushing. The server never merges
and never deletes either side. The full client algorithm, including the join
flow for a new device, is in [`sync-client.md`](sync-client.md).

## Security properties

| The server stores | The server never stores |
| ----------------- | ----------------------- |
| Encrypted blob bytes per version | Plaintext, hostnames, credentials |
| `SHA-256` of each token | Tokens themselves |
| Sizes, version numbers, timestamps | Master passwords, keys |

Consequences worth being explicit about:

- A database dump is not a credential leak: it holds ciphertext and token
  hashes. An attacker who gets the dump still needs a master password for the
  contents, and the token hash is not usable for authentication.
- A slot's existence, size and write times are visible to the operator.
  Hostnames and counts are not.
- TLS is the deployment's responsibility. The server speaks plain HTTP so it
  can sit behind any reverse proxy; plain HTTP is acceptable only on
  loopback, a LAN, or a VPN like Tailscale. Tokens are 256-bit, so guessing
  is not a practical attack even without rate limiting; exposing the server
  publicly still calls for TLS.
- `--create-secret` exists because a public server without it is free storage
  for anyone who finds it. It gates creation only; existing slots never need
  it.
- Losing a token loses the slot. There is no account recovery, by design.
  The operator can still rescue bytes from SQLite if they trust the person
  asking.

## Versioning policy

`/v1` is frozen. Additive changes — a new response header, a new field in a
JSON body, a new endpoint — are allowed without a version bump; clients must
ignore unknown headers and fields. Removing or changing existing behavior
requires `/v2`, and `/v1` keeps working for every client that shipped with
it.
